# AE350 P2 status

Latest JTAG investigation (2026-10-18): the round-14 launcher blocker is fixed
by correcting the fabric ROM's synchronous read/response timing. Final candidate
`658d75c21950...` has PnR 0/0 and passes ROM identity/nonsequential reads,
mailbox magic/ACK and CPU DDR eight-address read/write. See
[the investigation and exact receipts](ae350-jtag-launcher-investigation.md).

## Status update (round 9, 2026-10-18)

Adapter defects found by the audit are fixed and covered by a repo test,
`scripts/tests/test_ddr3_ahb.py` (23 checks, all PASS, interface stubs): window
capacity shadowing, read/write direction, response bit layout, `base`
translation, per-slave transaction gating with an address-phase-latched select,
ERROR2 recovery and DATA-state timeout. Simulation covers word/half/byte and
size-3 lane masks, upper-lane offsets, back-to-back transfers, window bounds,
unaligned and not-ready rejection, and recovery after each error.

Hardware trace (build `build/store/gateware/41662befcb57...`, setup 0 / hold 0,
DDR calibrated `0x00000203`): the adapter issues commands with correctly
translated addresses (`rec_cmd` `0x00000001` = read word 0 for CPU `0x2000`,
`0x00000009` = read word 1 for `0x2004`) and `rd_data_valid` pulses, but two
different addresses return the same value (`0xc88ad596`) and the written value is
never read back. Command/address translation is proven; write commit and
read-response-to-request association are not. Next step: explicit response-queue
accounting (single outstanding transaction, drop late responses after a timeout),
then a single-address write/read trace.

## Status update (round 10, 2026-10-18): bridge policy, adapter tests, recorder

**Test infrastructure.** `scripts/tests/test_ddr3_ahb.py` now runs 45 checks, all
PASS, against an interface-stub FIFO. The DDR model implements BL8 semantics
independently of the adapter: the command address selects the 32-byte block and
the low word bits select the lane inside the returned block, so the lane matrix
(`0x2000/0x2004/0x2008/0x200c` with distinct data) exercises the mapping instead
of agreeing with the adapter by construction.

**Bridge policy vs IP contract.** Aligning every command address to 8 words
(`ui.addr = (byte - base) >> 2 & ~7`) and selecting the lane from
`offset[3:5]`/`offset[0:5]` is *this adapter's* bridging policy. The vendor
reference increments the user address by 8 per 32-byte transfer, which is
consistent with block-aligned commands, but it is not proof that the IP rejects
unaligned start addresses. The IP documentation available in this repository
(`docs/ae350-p2-reference-notes.md`) states the address unit (4 bytes), one
32-byte beat per command and the mask semantics; it does not state a hard
alignment requirement. The model therefore encodes the BL8 data layout and the
adapter's alignment is documented as a deliberate restriction, not an IP rule.

**Pipelined AHB.** A true back-to-back pair (next address asserted during the
previous data phase, no IDLE) now yields two accepted commands with the correct
lane masks (`0x000f` and `0x0f00`), which exercises the address acceptance added
to the `COMPLETE`/`ERROR2` states. The pipelined driver does not yet model
HWDATA for the second transfer (a master-model limitation, stated in the test),
so back-to-back *data* is not claimed; single transactions verify data.

**Pre-fix hardware observations (build `41662befcb57...`, before block alignment
and the new recorder).** CPU `0x2000` produced UI address 0 and `0x2004`
produced UI address 1; two different CPU addresses returned the same value
`0xc88ad596`, whose low 32 bits match the vendor eye-pattern constant
`EYE_MEM[0] = 64'h5883adb4c88ad596`. These are baseline observations, not
evidence about the current implementation.

**Recorder.** The adapter now latches, per transaction: last write (command,
address, byte mask, low 64 bits of write data, counter) and last read (command,
address, the full 256-bit returned block, the selected 64-bit beat, counter).
They are exported through the ROM window at `0x8000_1FEC/1FE8/1FE4/1FE0/1FDC/
1FD8/1FD4/1FD0/1FCC/1FC8/1FC4/1FC0/1FBC`.

## Status update (round 11, 2026-10-18): DDR path proven at the adapter, CPU value still wrong

New 0/0 candidate `build/store/gateware/bea37aee52dd...` (PnR setup 0 / hold 0,
DDR calibration `0x00000203`). Root causes found and fixed in this round:

1. **Write mask was always all-ones at synthesis.** `wr_bytes` was computed as a
   dynamic shift of a dynamic-width constant; Migen simulation produced the right
   value while synthesis truncated it to zero, so every write was fully masked.
   Replaced with a Mux lookup sized by HSIZE and a shift by the low address bits.
   Hardware proof: a store to `0x2000` now shows `rec_w_mask = 0xfffffff0` and
   `rec_w_data = 0x11223344`, and the same address reads back `0x11223344`
   (`rec_r` read at block 0, selected beat `0x11223344`).
2. **HWDATA was sampled one cycle too early.** The AHB master drives write data
   in the cycle after the address phase; the adapter captured it in the first
   cycle. Added a data-phase alignment cycle. Hardware proof: the recorded write
   data changed from the previous transaction's value to the value actually
   stored.
3. **Command addresses are block aligned** (`addr & ~7`) with the lane selected
   by mask; verified on hardware for `0x2000` and `0x2004` (masks `0xfffffff0`
   and `0xffffff0f`, both commands to block 0, both values read back correctly).

**Still open.** In a CPU program that stores `0x11223344` to `0x2000` and
immediately loads it back, the DDR side is correct (`rec_w`/`rec_r` above) but
the CPU-visible result is the instruction word at the program's entry
(`0xddd007b7`), which the disassembly shows is not what the C-level store writes.
The disassembly confirms the program itself is correct, so the remaining defect
is in the fabric data path between the adapter response and the AE350 LSU,
most likely the `psel`/`pending` response selection when an instruction fetch and
a data load are in flight together. A registered copy of the DDR response
(`ddr_rdata_q`) did not change the outcome and does not break SRAM fetch.

Final candidate for this milestone: `build/store/gateware/b09e9335f728...`

**Root causes closed in this round**

| Symptom | Root cause | Fix |
| --- | --- | --- |
| every write fully masked | `wr_bytes` was a dynamic shift of a dynamic-width constant; simulation produced the right value, synthesis truncated it to zero | Mux lookup sized by HSIZE, shifted by the low address bits |

**Simulation** (`scripts/tests/test_ddr3_ahb.py`, interface-stub FIFOs, independent
BL8 model): 49 checks, all PASS. Coverage: word/half/byte/size-3 lane masks,
upper-lane offsets, same-block offsets 0x2000/0x2004/0x2008/0x200c, true

rejection, recovery after each error, DDR-side stall producing a bounded error,
backpressure (command accepted on alternate cycles) and read-after-timeout
isolation.

**Hardware, final candidate**

* CPU program (code 0x1000, stack 0x1a00, results 0x1900): store 0x2000 =
  0x11223344 then load it back -> `RES[0]=0xddd00001`, `RES[1]=0x11223344`,
  `RES[2]=0xddd00002`.
* Multi-address CPU program: eight addresses (0x2000/0x2004/0x2020/0x2028/
  0x2100/0x2104/0x3000/0x3004) with distinct values -> `errors=0`, 8/8 pairs
  match.
* Same 32-byte block through CPU JTAG: 0x2000/0x2004/0x2008/0x200c with
  0x11112222/0x33334444/0x55556666/0x77778888 -> all read back correctly;
  write masks 0xfffffff0 / 0xffffff0f / 0xfffff0ff / 0xffff0fff; recorder write
  command always cmd=0 at block 0; read commands cmd=1 at block 0.
* Per-transaction recorder read over the ROM window: `rec_w` (cmd|addr),
  `rec_w_mask`, `rec_w_data[0:32]`, `rec_r` (cmd|addr), `rec_r_sel[0:32]`,
  `rec_r_blk[0:64]`, `rec_w_n|rec_r_n` at 0x8000_1FEC/1FE8/1FE4/1FE0/1FDC/1FD8/1FD4/1FD0.

**Known recorder limitation**: `rec_w_data` exports only the low 32 bits of the
256-bit write data, so writes to lanes above bit 31 show 0 in that field; the
mask and the read-back values carry the proof for those lanes. Extending the
window to the full 256 bits is a follow-up (the current ROM mux depth was the
timing limit at 100 MHz).

**Still not accepted**: capacity/aliasing beyond the exercised addresses, cache
maintenance, execution from DDR, per-frequency sweep, 30-minute stress,
performance numbers, UART console (still silent; all evidence above is CPU JTAG).

**Why the hard macro cannot be simulated**: Gowin's `IDE/simlib/gw5a/prim_sim.v`
declares `AE350_SOC` as a port-only module with no behaviour, and the DDR3 PHY
ships as synthesis netlists without a behavioural model, so no installed flow can
simulate the CPU or the PHY. What is simulatable - the AHB adapter, the address
decode and the response mux - is covered by the 49-check test above, which is
where three of the five defects in this table were found (the mask truncation and
the select/hold race were only visible on hardware because the testbench modelled
the master incorrectly; that master model is now protocol-correct).

## Round 14 — corrections to the JTAG diagnosis, duplicate-Signal fix, test cleanups

1. **`08000404` is an abstract-command / hart-state error, not a USB or FTDI
   failure**; the earlier FTDI-handle attribution is withdrawn. Measured
   sequence (build `39e80d78b453`, receipt
   `build/runs/<ts>Z-jtag-sequence/sequence.json`): open → dmstatus `00430ca2`
   (running); write dmcontrol `80000001` → `004303a2` (allhalted); DPC reads
   `800000b0`; abstract ROM read at `0x80000000` succeeds; then writing
   dmcontrol `00000001` (haltreq cleared, no resumereq) leaves dmstatus at
   `004303a2` (still allhalted) and memory access still works; only dmcontrol
   `40000001` (resumereq) moves to `00430ca2` (running). The observed failures
   came from doing abstract accesses while the hart was running (the harness
   polled memory right after `resume()`), so `ae350_jtag.halt()` now keeps
   haltreq as a bookkeeping choice and the comment no longer claims an AE350
   quirk. Note `close()` intentionally resumes; any cleanup path resumes the
   hart.
2. **Duplicate `self.recovering` (real defect, fixed).** The AHB state machine
   created the signal twice, so `bad` referenced the first object while DRAIN
   drove the second. It is now created once.
3. **DRAIN reworked.** It holds `HREADY` low for the whole recovery window, so
   no address can be accepted-and-dropped while recovering; it leaves only when
   the DDR engine reports no outstanding transfer (synchronised into the fabric
   domain with MultiReg), and a bounded fail-safe moves to a `DEAD` state that
   returns ERROR for DDR until reset.
4. **Late-response test fixed**: it no longer accepts "error or success"; it
   asserts that A's read command was actually handshaked before the delay, that
   A returns the timeout error, and that A never returns the stale value.
5. **HOLD assumptions removed** from `ahb_pipelined()` and the inline
   back-to-back block; the driver holds the next address until the completion
   edge (standard AHB), and the comment no longer describes a hold cycle.
6. New builds: `39e80d78b453` (setup/hold 0/0, JTAG launcher monitor) and
   `a3b177865ce3` (setup/hold 0/0, monitor also disables caches at boot).
   **On hardware the launcher handshake still fails**: after resume the hart
   loops at `0x8000008c` in the monitor but does not observe the magic written
   to `0x1800` (the same address reads back the written value through the DM).
   Core-view vs DM-view aliasing (internal DTCM versus fabric SRAM) is the
   leading hypothesis and is **not proven**. Historical write/read evidence
   (build `b09e9335f728`) remains the last verified on-board result; the new
   RTL is still unverified on hardware.

Result: the launcher handshake works (`ack=0xa55a0001`) and the CPU executes
from DDR (`pc=0x303c`/`0x3050` in the payload image), but the payload stops
before its first result write. A 42-byte minimal DDR-resident program reproduces
it: `RES[0]=0xd0000001` is written, the store to `0x2000` does not read back
(`RES[1]=0`), and the final marker is corrupted (`0xd0003002`). The recorder
shows the DDR adapter received a **write at UI word address 0x408, i.e. CPU
address 0x3020** (the payload's own code region) with a mask for that offset,
and a matching read — a transaction the program never issues. So with code
executing from DDR, an SRAM store is misrouted into the DDR adapter (the
fabric select / address pairing for interleaved fetch+data traffic), and the
SRAM word is corrupted by the DDR response.

This is a decoder bug in `mega138k_ae350_p2.py`, not an adapter or DDR issue:
the earlier verified result (`b09e9335f728`) ran code from SRAM, where fetch and
data traffic did not interleave across the two slaves. Next: make the decode
pair the accepted address phase with its own slave for both the request and the
response (register the selected slave together with the address and hold it for
the whole transfer), add a simulation test for interleaved fetch/data, then
re-run `ddr-suite`.

## Round 16 — root cause of the DDR-resident failure: 7-bit lane shift in the adapter

Two changes this round, both verified.

**1. Interconnect rewritten (`gateware/machines/ae350_interconnect.py`).**
One master, priority-decoded slaves, and a single address-acceptance rule
`accept = HTRANS[1] & hit & HREADY`.  The address, direction and size are
captured together with the selected slave; the response mux is driven by the
slave captured for the transfer in its data phase; a valid next address in the
completion cycle is accepted there (no hold cycle); an unmapped address is
handled by a two-cycle `ErrorSlave`.  Joint simulation
(`scripts/tests/test_ae350_interconnect.py`, 14 checks PASS) covers SRAM and DDR
through one master: alternating fetch/data traffic, DDR read after SRAM write,
SRAM read after DDR read, completion-cycle slave switching, unmapped-address
error and recovery, and "every accepted address reached exactly one slave".

**2. The hardware failure was a Migen width bug, not the decode.**
The generated Verilog contained
`gowinddr3_rd_data >>> (ddr_port_offset[4:3] * 7'd64)`: the constant was sized
to 7 bits, so `2 * 64 = 128` wrapped to 0 and beat index 2/3 aliased onto beat 0.
Consequence: within every 32-byte transfer, offsets 0x10/0x30 read back as the
block's lane-0 word and the corresponding writes were mis-laned, which corrupted
DDR-resident code on load (the first `illegal instruction` at 0x3010) and made
stores/loads look like fabric ghosts.  The shift amount is now an explicit
9-bit signal (`lane * Constant(64, 9)`), used by the read mux, the write-data
shift and the recorder.

Hardware evidence on build `82cda6d6a0c6` (setup/hold 0/0):

| Check | Result |
| --- | --- |
| DM 4-offset same block (0x3000/10/20/30) | 4/4 exact |
| SRAM-resident `board jtag-test` | PASS, CPU DDR 8/8 |
| DDR-resident program, SRAM stores only | results 0x11111111/0x22222222/0xd0000002, mcause 0, code bytes changed 0 |
| DDR-resident program with DDR store+load | read back 0xa5a5a5a5, code checksum identical before/after (0x365bd074), mcause 0, code bytes changed 0 |
| Full payload from DDR | executes (PC 0x3c9c, mcause 0), first six checks PASS; completion under investigation (stress test duration) |

The earlier "SRAM store misrouted into the DDR adapter at 0x3020" reading was
wrong: the recorder's address was a DM payload load, and the actual defect was
the lane shift above.

## Round 23 — byte-level coverage and the fabric observer

**Byte-level traversal coverage** (`--flags 11 --traversal-mb 64`, build
`dab2ddfa899e`, receipt `build/runs/20261018T140338970314Z-board-ae350-ddr-suite`):

## Round 24 — cache semantics measured with the fabric observer (write-back)

The recorder's counters were 8-bit and packed, which is why the earlier numbers
looked odd; they are now separate 16-bit words (`0x80001FCC` reads,
`0x80001FC8` writes). Build `78e4753d5b6c`, receipt
`build/runs/20261018T155414064703Z-board-ae350-ddr-suite`, payload flag bit 2:

| step | read counter | write counter |
| --- | --- | --- |
| refill of one word with L1D on | +8 | |
| immediate second access | **+0 (cache hit)** | |
| after `L1D_INVAL_ALL`, one access | +10 | |
| store with L1D on | | **+0 (dirty in cache)** |
| after `L1D_WB_ALL` (clean) | | **+4 (write-back)** |

`errors=0` for the composed check (hit produces no fabric traffic, bypassed read
does, dirty store stays off the bus, clean writes it back). **This corrects the
earlier "write-through" statement**: the L1D is write-back. The earlier
`pre_clean` observation that looked like write-through is explained by
`mcache_ctl.DC_EN` being cleared before that read — disabling the D-cache flushes
dirty lines. Both facts are compatible: a cached store does not touch DRAM
(observer), and disabling the cache makes it visible.

## Round 25 — LR/SC vs AMO measured, stress timing and a core-clock estimate

**Atomics on fabric memory are not supported by this SoC configuration.** The
vendor AE350 wrapper's data port (`riscv_ae350_soc_tmp.v`) exposes only
`HADDR/HBURST/HPROT/HSIZE/HTRANS/HWDATA/HWRITE/HRDATA/HREADY/HRESP` — no
`HEXOKAY`, `HLOCK` or `HMASTLOCK` — and our fabric returns a single-bit `HRESP`.
Measured with a minimal SRAM-resident program on build `78e4753d5b6c`:

* `lr.w`/`sc.w` at SRAM `0x40001000`: `sc.w` raises a store/AMO access fault,
  `mcause=6`, `mepc=0x4000103a`, `mtval=0x11111111`;
* `amoadd.w` at SRAM `0x1940` and DRAM `0x102004`: the hart stops on the AMO
  instruction, `mcause=0`, and the DDR recorder shows no transaction for it.

So G8's "integer and supported aligned LR/SC/AMO" clause cannot be met on
fabric memory here; the payload records `amo_supported=0` and exercises a plain
RMW. This is a hardware-configuration limit, measured on both directions of the
port, not an acceptance pass.

**Stress timing is now host-measured.** `board ddr-suite` takes
`--poll-interval` (default 0.15 s) and records `host_wall_seconds`,
`host_paused_seconds` (the sum of every halt during polling) and
`host_running_seconds`. A 300 s stress at `--poll-interval 2`
(`build/runs/20261018T155626560159Z`): wall 310.5 s, paused 0.25 s, running
310.2 s — the CPU's own mcycle budget (300 s × 800 MHz) therefore corresponds to
roughly 774 MHz average, i.e. the configured 800 MHz core clock with about 3%
error. That is a measured core-frequency estimate for the P1 item that was still
open; it is mcycle-derived and is reported as such.
