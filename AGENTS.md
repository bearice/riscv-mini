# Repository workflow

## Build workspace iron rule

Repeated builds of the same machine/target MUST reuse the SAME workspace. This includes source edits, parameter tuning, timing closure, failed-build retries and verification rebuilds. Keep the existing `--workspace` value; use `default` when none was selected. NEVER create a new workspace name per attempt, phase, timestamp, purpose or parameter combination. Preserve the workspace and its compiler/Ninja/Gowin caches between builds. Use `--purpose` and automatic run receipts to distinguish attempts. Serialize repeated builds in that workspace; do not create new workspaces just to run retries concurrently.

For basic operations (find/build artifacts, observe/recover the board, RAM run, persistent update, verification), start with `scripts/mini.py --help` and [the task guide](scripts/README.md). Use its operation workflows rather than composing programmer/UART calls or writing temporary probes. Operation and test receipts live in `build/runs/`; historical `build/operations/` is retained.

For component reuse, environment discovery, portable locks or source replay, read [component builds](docs/common/component-builds.md). For 20K BIOS-only builds, use `mini.py build bios --hardware <20K-system>` to retain selected hardware; `plan` explains reuse. New candidates keep `current` unchanged. All builds use `mini.py build <target>` and `mini.py plan <target>`, including hardware generation, CPU and upstream OS/payload targets. Do not add standalone build entry points or prepare/record wrappers. Historical recipes execute their own preserved checkout through `mini.py builds reproduce`.

Read the operation-specific skill when performing that operation: [构建与 PnR](.agents/skills/riscv-mini-build/SKILL.md), [测试与实板验收](.agents/skills/riscv-mini-test/SKILL.md), [性能测试与对比](.agents/skills/riscv-mini-benchmark/SKILL.md), [整理与提交](.agents/skills/riscv-mini-commit/SKILL.md), [发布与最终归档](.agents/skills/riscv-mini-release/SKILL.md), [清理中间构建](.agents/skills/riscv-mini-clean/SKILL.md), [复现构建](.agents/skills/riscv-mini-reproduce/SKILL.md). Load only the skills needed for the task.

Before preparing or creating a Git commit, read [the pre-commit SOP](docs/common/pre-commit-sop.md). Ordinary commits require reviewing and explicitly staging the intended changes and passing `git diff --cached --check`; tests, builds, PnR, board/performance validation, change records, staged fingerprints and post-commit snapshots are not mandatory commit gates. Perform targeted checks when the task needs them or the user requests them. Run the full release workflow only when the user explicitly requests a real release. Update versions and CHANGELOG only for releases; do not duplicate Git file inventories in reports. Read [version history](docs/common/version-history.md) when assigning a release version.

For build discovery, performance comparisons or board programming, read [build artifact organization](docs/common/build-artifacts.md). Select an explicit build identity and baseline; verify the machine of every reference, including `current`, before using it as the qualified board version.

Platform documentation is indexed in [docs/README.md](docs/README.md). Shared rules live in `docs/common/`; machine-specific facts and operations live in `docs/platforms/<machine>/`. Select the machine workflow before board operations; do not apply 20K BIOS/XIP/Flash rules to AE350. For iterative board testing, use FPGA SRAM and the machine's UART loader. Never write board Flash unless explicitly requested.
